## 0. The problem with naive multi-chain

Landfall's whole reason to exist is: **you cannot fake on-chain settlement history.**
On Stellar that is literally true — SEP-24 anchors leave deposit/withdrawal traces on a
cheap, publicly replayable ledger, and since Protocol 23 (CAP-67) every value-moving
operation emits a *standardized* event. Reading that ledger is ground truth.

That property does **not** hold uniformly on other chains:

- On Ethereum/L2s the fiat leg is mostly custodial; the only verifiable artifact is a
  stablecoin mint/burn (e.g. Circle CCTP burn + Iris attestation + destination mint).
- On Tron/Solana, USDT/USDC transfers are visible but the fiat on/off-ramp itself is
  opaque (exchange/gateway custody).

So if we "just index more chains," Landfall silently degrades from *proof* to *guessing*,
and loses the one thing that makes it credible.

**The way around this is not to weaken the thesis — it's to build a new primitive that
carries the thesis across chains.**

---

## 1. Core idea: the Keystone-Chain model

We introduce **Landfall STP (Settlement Truth Protocol)**: a chain-agnostic settlement
*attestation* schema, plus per-chain *adapters*, plus a Soroban *anchor oracle*.

- **Stellar is the keystone chain.** It is the one chain where Landfall can produce
  cryptographically verifiable ground truth cheaply, at full history, with standardized
  events. Every score, every attestation, ultimately roots back to a Stellar record.
- **Other chains are attested, not assumed.** For each non-Stellar chain, the adapter
  binds whatever verifiable artifact *does* exist (a CCTP burn hash, a LayerZero DVN
  attestation, a zkTLS proof of a custodial API response) into the same attestation
  schema — and **labels its evidence tier honestly** (see §4). We never present a
  custodial guess as if it were ledger truth.

This keeps the "can't fake it" promise: on Stellar it's proven; on other chains the
attestation states *exactly* what class of evidence backs it, and anchors that trust back
to Stellar wherever a cross-chain settlement touches Stellar (CCTP burn↔mint, bridge msg).

```
                 ┌─────────────────────────────────────────────┐
                 │            Landfall STP (schema)             │
                 │   one signed "settlement attestation" shape  │
                 └─────────────────────────────────────────────┘
                          ▲                 ▲               ▲
             ┌────────────┘        ┌────────┘      ┌────────┘
   ┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
   │ Stellar adapter  │  │  EVM adapter     │  │  Tron / Solana   │
   │  (KEYSTONE)      │  │ (CCTP / LZ DVN)  │  │   adapters       │
   │ ledger truth     │  │ mint/burn+attest │  │ transfer+zkTLS   │
   │ Tier: PROVEN     │  │ Tier: ATTESTED   │  │ Tier: DERIVED    │
   └──────────────────┘  └──────────────────┘  └──────────────────┘
```

## 2. Layer breakdown (unchanged names, now multi-chain aware)

| Layer | What it is | Chain scope | Status |
|------|-------------|-------------|--------|
| **L1 — Ledger truth** | Index the ledger, compute liveness / fulfilment / refund / concentration | Stellar only (keystone) | ✅ built |
| **L2 — Attested outcomes** | Portable signed settlement receipts (STP schema) covering the fiat leg | **all chains** | 🔨 build next — this is the cross-chain primitive |
| **L3 — Distribution** | `pickAnchor()` SDK, public API, MCP server, **Soroban oracle** publishing signed score digests | reads all, publishes on Stellar | 🔨 build after L2 |

The insight: **L1 is chain-specific and strong; L2 is inherently portable.** A signed
attestation does not depend on any single chain's ledger semantics, so L2 — not L1 — is
what generalizes. Multi-chain is unlocked by making L2 a first-class, EAS-style primitive
with Stellar as the reference implementation.

## 3. The STP attestation schema

One schema, emitted the same way on every chain (EAS-style on EVM, Soroban-native struct
on Stellar). All fields required unless marked optional.

```jsonc
{
  "stp_version": "1",
  "anchor_id": "string",          // canonical Landfall anchor id (see §5)
  "chain": "stellar|ethereum|base|arbitrum|optimism|polygon|solana|tron",
  "asset": "string",              // e.g. "USDC", "USDT", "MGUSD"
  "direction": "deposit|withdrawal|bridge_in|bridge_out",
  "amount": "string",             // decimal string, asset units
  "onchain_ref": "string",        // tx hash / operation id on `chain`
  "fiat_leg_ref": "string|null",  // optional: provider ref / receipt id (may be hashed)
  "evidence_tier": "PROVEN|ATTESTED|DERIVED",   // see §4 — never omit, never inflate
  "evidence_detail": "string",    // e.g. "stellar_ledger", "cctp_burn+iris", "zktls_api"
  "keystone_ref": "string|null",  // Stellar tx hash this settlement roots to, if any
  "observed_at": "ISO-8601",
  "signer": "string",             // Landfall attester key id
  "sig": "string"                 // signature over the canonical serialization
}
```

Design rules:
- **`evidence_tier` is mandatory and must match reality.** The whole product dies if this
  is ever inflated. A DERIVED attestation must never be rendered as if PROVEN.
- **`keystone_ref`** is populated whenever the settlement touches Stellar (e.g. a CCTP
  mint on Stellar, a bridge message delivered to Stellar). This is what "anchors back to
  the keystone" means mechanically.
- Serialization must be canonical (deterministic key order) so signatures are reproducible.

---

## 4. Evidence tiers (the honesty ladder)

| Tier | Meaning | How it's obtained | Example chains |
|------|---------|-------------------|----------------|
| **PROVEN** | Read directly from an immutable, publicly replayable ledger with standardized events | Stellar ledger via Galexie/CDP or events-exposing RPC | Stellar |
| **ATTESTED** | Backed by a signed, independently verifiable cross-chain artifact | CCTP burn + Circle Iris attestation; LayerZero DVN attestation | EVM chains, cross-chain flows |
| **DERIVED** | Inferred from visible transfers + a bound off-chain proof; fiat leg is custodial | on-chain transfer + zkTLS/Proof-of-Reserve proof of the custodial API | Tron, Solana, custodial ramps |

Rendering rule everywhere (API, SDK, UI): **show the tier next to the number.** Headline
scores may be computed per-tier and must never blend PROVEN and DERIVED into one figure
without labeling the mix.

## 5. Canonical anchor identity (works across chains)

Before any cross-chain scoring, resolve a stable `anchor_id`:

1. Parse the anchor's **SEP-1 `stellar.toml`** (`SIGNING_KEY`, `ACCOUNTS`,
   `TRANSFER_SERVER_SEP0024`, `CURRENCIES`, and `WEB_AUTH_FOR_CONTRACTS_ENDPOINT` for
   SEP-45 contract-account anchors) to map anchor → Stellar accounts → assets.
2. Reconcile against the SDF Anchor Directory + stellar.expert.
3. For non-Stellar presence, map the operator's known contract/issuer addresses per chain
   into the same `anchor_id` via a maintained `anchors.registry.json`.

`anchor_id` is the join key across all adapters.

## 6. Adapter interface

Every chain adapter implements the same interface so L2/L3 don't care which chain they're
reading.

```ts
// packages/adapters/src/types.ts
export type EvidenceTier = "PROVEN" | "ATTESTED" | "DERIVED";

export interface SettlementEvent {
  anchorId: string;
  chain: string;
  asset: string;
  direction: "deposit" | "withdrawal" | "bridge_in" | "bridge_out";
  amount: string;
  onchainRef: string;
  fiatLegRef?: string | null;
  evidenceTier: EvidenceTier;
  evidenceDetail: string;
  keystoneRef?: string | null;
  observedAt: string; // ISO-8601
}

export interface ChainAdapter {
  chain: string;
  /** highest tier this adapter can ever emit */
  maxTier: EvidenceTier;
  /** stream/enumerate settlement events for an anchor over a range */
  scan(anchorId: string, opts: ScanOpts): AsyncIterable<SettlementEvent>;
  /** verify a single artifact independently (used by attestation signing) */
  verify(ev: SettlementEvent): Promise<boolean>;
}

export interface ScanOpts {
  fromLedgerOrBlock?: number | string;
  toLedgerOrBlock?: number | string;
  minAmount?: string;
}
```

Adapters to build, in order:
1. **`stellar` (keystone, maxTier: PROVEN)** — refactor existing L1 code behind this
   interface. Source: Galexie/CDP data lake or an events-exposing Stellar RPC (NOT SDF
   Horizon, which does not expose Stellar Events — see §8).
2. **`evm-cctp` (maxTier: ATTESTED)** — Circle CCTP burn events + Iris attestation +
   destination mint. Covers Ethereum, Base, Arbitrum, Optimism, Polygon. CCTP went live on
   Stellar 2026-05-19, so cross-chain USDC flows to/from Stellar populate `keystone_ref`.
3. **`tron` (maxTier: DERIVED)** — USDT transfers via TronGrid; fiat leg bound by zkTLS /
   Proof-of-Reserve proof. Tron carries ~$88B USDT, the dominant real-world rail.
4. **`solana` (maxTier: DERIVED)** — USDT/USDC transfers; CCTP where available.

## 7. Layer 3 — Soroban anchor oracle (publishes on the keystone)

- Publish signed **score digests** on Stellar via a Soroban contract, shaped to the
  **SEP-40** oracle consumer interface so Blend pools, wallets, and agents can read anchor
  reliability with zero custom integration.
- Model the push mechanism on **Reflector**: emit an on-chain proof when a threshold event
  fires (e.g. an anchor crossing from live → dark), plus periodic digest updates.
- Emit contract events using the **SEP-48** event schema so indexers (Mercury/Zephyr) can
  consume them.
- Use **Soroban constructors (CAP-58)** for one-shot init; keep state small to exploit
  Protocol 23 in-memory state / archival cost reductions.
- Consumers get: `get_score(anchor_id) -> {score, tier_mix, last_update, digest}`.

`pickAnchor()` SDK and the public API/MCP server read this oracle plus the L2 attestation
store.

---

## 8. Data-integrity notes (do not skip)

- **Source of events matters.** SDF Horizon does **not** expose Stellar Events. Use a
  Galexie-exported data lake (getLedgers over the lake) or an events-exposing RPC.
- **Reconciliation caveat.** Between Protocol 23 and 24 (Oct–Nov 2025) some Stellar Events
  were omitted until Stellar Core v24.1.0; anyone reading a lake from that window must
  re-export/reprocess. Document which source and window Landfall reads.
- **Heuristics stay labeled.** Refund detection and "no settlement in N days" must parse
  path payments, claimable balances, muxed accounts, and SAC/contract transfers before
  flagging an anchor dark, or they produce false positives.

## 10. Build plan (do these in order)

1. **Extract the adapter interface** (`packages/adapters/src/types.ts`) exactly as §6.
2. **Refactor existing L1** into `packages/adapters/stellar` implementing `ChainAdapter`
   with `maxTier: "PROVEN"`. No behavior change; just move behind the interface. Keep the
   19 tests green.
3. **Build `packages/stp`**: the schema (§3), canonical serialization, `sign()` / `verify()`,
   and `stp.schema.json`. Unit-test round-trip + signature reproducibility.
4. **Build `evm-cctp` adapter** (§6.2): read CCTP burn events, fetch Iris attestation,
   confirm destination mint, emit `ATTESTED` events; populate `keystoneRef` when Stellar is
   source or destination. Mock the Iris API in tests.
5. **Add SEP-1 identity resolution** (§5) + `anchors.registry.json`.
6. **Build the Soroban oracle** (§7) on testnet: SEP-40-shaped reads, SEP-48 events,
   CAP-58 constructor, threshold on-chain proof à la Reflector.
7. **`pickAnchor()` SDK + public API + MCP server** reading oracle + attestation store,
   always surfacing `evidence_tier`.
8. **`tron` then `solana` adapters** (`DERIVED`) once schema is stable; bind zkTLS/PoR
   proofs for custodial legs.

Acceptance for "multi-chain works end to end": Stellar (PROVEN) + one EVM chain via CCTP
(ATTESTED) both produce reproducible, independently verifiable STP attestations for the
same `anchor_id`, and the Soroban oracle publishes a combined, tier-labeled score digest.
